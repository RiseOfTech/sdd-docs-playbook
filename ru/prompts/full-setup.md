# Задача: внедрить в проект читаемую документацию и слежение за ней

Ты — ИИ-агент. Ты работаешь в репозитории проекта.
Прочитай эту инструкцию полностью. Затем выполняй этапы по порядку.

---

## 0. Главные правила (соблюдай всегда)

1. Выполняй этапы строго по порядку. Не пропускай этапы.
2. После каждого этапа обнови файл `docs/_setup/progress.md`.
3. На шагах с пометкой **СТОП** покажи результат пользователю. Жди ответа. Не продолжай без ответа.
4. Не изменяй код программы. Ты работаешь только с документацией и инструкциями.
5. Не изменяй формат существующих спецификаций. Ты можешь только читать спецификации.
6. Не придумывай имена классов, методов, файлов, полей.
   Каждое имя в документации копируй из файла, который ты открыл в этой сессии.
7. Если ты не уверен в факте, напиши в тексте `[ПРОВЕРИТЬ: <что именно>]`. Не угадывай.
8. Обрабатывай одну область (capability) за один раз. Не держи в работе несколько областей.
9. Не делай коммиты и не создавай ветки, если пользователь не попросил.
10. Если инструкция противоречит правилам проекта (`AGENTS.md`, `CLAUDE.md`, `GIGACODE.md` и т. п.), остановись и спроси пользователя.
11. Если корень документации не `docs/` (шаг 1.0), во всех путях и текстах этого промпта замени `docs/` на корень документации.

**Если работа прервалась:** открой `docs/_setup/progress.md`. Если файла нет, найди в проекте файл `_setup/progress.md`. Продолжи с первого незавершенного шага.

## 1. Что ты строишь

Механизм состоит из семи частей:

| № | Часть | Файл | Для чего |
|---|---|---|---|
| 1 | Правила | `docs/DOCS-RULES.md` | Единые правила письма и сопровождения. Все навыки и агенты ссылаются на этот файл. |
| 2 | Карта | `docs/MAP.md` | Области проекта и документы по каждой области. Человек, который не знает проект, начинает с этого файла. |
| 3 | Маршрут | `docs/ONBOARDING.md` | Что читать каждой роли и в каком порядке. |
| 4 | Словарь | `docs/glossary.md` | Термины проекта. Один термин = одно значение. |
| 5 | Гайды | `docs/guide/<область>/analyst.md` и `dev.md` | Короткие объяснения для аналитика и разработчика. |
| 6 | Шаблоны | `docs/guide/_template/` | Заготовки гайдов. |
| 7 | Встраивание | навык / правила агента / конфиг SDD | Чтобы гайды обновлялись при каждом изменении. |

Главная идея: **правила записаны один раз в `docs/DOCS-RULES.md`.**
Навыки, конфиги и инструкции агентов не копируют правила. Они только ссылаются на этот файл.

## Этап 1. Изучи проект

Цель: понять, что за проект и какие инструменты уже есть.
Ничего не создавай, кроме файлов отчета.

### Шаг 1.0. Выбери корень документации

Корень документации — папка, в которой лежат все файлы документации. По умолчанию это `docs/`.

1. Проверь корень проекта. Найди папки с файлами `.md`, например `docs/`, `documentation/`, `wiki/`.
2. Если папки `docs/` нет, а другая папка с документацией есть, остановись. Спроси пользователя: "Документация проекта лежит в `<папка>/`. Создать файлы документации в ней или в новой папке `docs/`?"
3. Запиши ответ. Это корень документации.
4. Если корень документации не `docs/`, во всех путях и текстах этого промпта замени `docs/` на корень документации. Пример: `docs/_setup/inventory.md` станет `documentation/_setup/inventory.md`.

В остальных случаях корень документации — `docs/`.

### Шаг 1.1. Найди файлы и запиши, что нашел

Проверь каждый пункт. Для каждого запиши: "есть" (путь) или "нет".

**Сборка и язык:**
- `build.gradle`, `build.gradle.kts`, `settings.gradle*`, `pom.xml`, `package.json`, другие.
- Модули проекта (из `settings.gradle` или `pom.xml`).

**Спецификации (SDD):**
- `openspec/` — OpenSpec. Запиши: `openspec/specs/*`, `openspec/changes/*`, `openspec/config.yaml`.
- `.specify/` или `specs/` — Spec Kit или другой инструмент.
- Другие папки со спецификациями или требованиями.

**Инструкции для агентов:**
- `AGENTS.md`, `CLAUDE.md`, `GIGACODE.md` (в корне и в подпапках).
- `.claude/skills/*/SKILL.md`, `.claude/commands/*`, `.claude/agents/*`.
- `.gigacode/skills/*/SKILL.md`, `.gigacode/commands/*`.
- `.opencode/skills/*/SKILL.md`, `.agents/skills/*/SKILL.md`.
- `.cursor/rules/*`, `.github/copilot-instructions.md`, другие файлы с правилами для ИИ.
- Правила и навыки вне репозитория. Признак: файл инструкций ссылается на путь вне проекта, например `~/.config/<инструмент>/AGENTS.md` или `~/.claude/skills/`. Запиши путь. Не открывай файл. Добавь вопрос пользователю: учитывать ли этот файл.

**Документация:**
- `README.md`, `docs/`, `wiki/`, `adr/`, другие папки с `.md`.
- Словари и списки терминов. Ищи и отдельные файлы, и разделы внутри документов. Например, раздел "Термины" в `README.md`. Запиши путь и название раздела.

**Язык документации:**
- На каком языке написаны спецификации и документация проекта.

**Предметная область (поиск):**
- Главные пакеты с бизнес-логикой (например, `domain`, `service`, `model`).
- SQL-скрипты, схемы данных.

### Шаг 1.2. Прочитай найденные навыки, правила и документы

Для каждого навыка и файла правил запиши одну строку:
`<путь> — <что делает> — <когда запускается>`.

Отметь навыки, которые связаны с: ревью, задачами, спецификациями, документацией.

Для каждого документа из раздела "Документация" шага 1.1 выбери оценку:
- "актуален" — факты из документа совпадают с кодом;
- "частично устарел" — часть фактов не совпадает с кодом;
- "устарел" — документ описывает поведение или процесс, которых больше нет;
- "неизвестно" — ты не смог сверить факты.

Чтобы выбрать оценку, сверь с кодом 2–3 факта из документа: имена классов, настройки, зависимости. Запиши основание: какой факт совпал или не совпал.

### Шаг 1.3. Определи области (capability)

- Если есть `openspec/specs/<имя>/`, каждая папка = одна область.
- Если есть другой SDD-инструмент, используй его деление.
- Если SDD-инструмента нет, добавь вопрос пользователю: "Библиотека рассчитана на проекты со SDD. В проекте не найден SDD-инструмент. Продолжать?" Предложи области по модулям или пакетам бизнес-логики.
- Если спецификации разбиты по этапам работы, а не по областям, не используй их деление. Предложи области по коду. Добавь вопрос пользователю.

Запиши список областей. Для каждой: имя, путь к спецификации (если есть), пути к коду.

Пути к коду:
- Если у области своя папка или пакет, запиши путь к нему.
- Если код разделен по слоям (например, `controller`, `service`, `repository`), у всех областей одни и те же пакеты. Тогда запиши для каждого слоя файлы области или маску имен. Пример для сервиса библиотеки: `service/Loan*`, `repository/LoanRepository.java`.
- Каждый путь относится только к одной области. Если файл нужен двум областям, добавь вопрос пользователю.

## Этап 2. План встраивания

Цель: решить, как механизм соединится с тем, что уже есть.

### Шаг 2.1. Реши для каждого существующего навыка

Для каждого навыка, связанного с ревью, задачами, спецификациями или документацией, выбери одно действие:

| Действие | Когда выбирать |
|---|---|
| **Оставить** | Навык не касается документации. |
| **Добавить ссылку** | Навык делает ревью или закрывает задачи. Добавь в него 1–3 строки: "Проверь гайды по `docs/DOCS-RULES.md`, раздел 7 "Проверка"". |
| **Заменить** | Навык уже делает похожую документацию, но хуже. Предложи заменить. Не удаляй сам. |

Правило смешивания навыков:
- Не копируй текст правил в другие навыки. Только ссылка на `docs/DOCS-RULES.md`.
- Один навык = одна задача. Не объединяй ревью кода и написание гайдов в один навык.
- Если два навыка противоречат друг другу, запиши противоречие в план. Не исправляй сам.

### Шаг 2.2. Реши, куда встроить обновление гайдов

Выбери все подходящие строки таблицы.

| Если в проекте есть | Встрой так |
|---|---|
| `openspec/config.yaml` | Добавь `context` и `rules` (текст в этапе 8). |
| Другой SDD-инструмент с шаблоном задач | Добавь в шаблон задач пункты из этапа 8.1, ключ `tasks`. Запиши в план путь к файлу шаблона. |
| `AGENTS.md`, `CLAUDE.md` или `GIGACODE.md` | Добавь короткий раздел со ссылкой на `docs/DOCS-RULES.md`. |
| Папка навыков | Создай навыки `docs-sync` и `docs-review` (текст в этапе 8). Имя папки зависит от инструмента: Claude Code — `.claude/skills/`, GigaCode — `.gigacode/skills/`, OpenCode — `.opencode/skills/`, общая папка — `.agents/skills/`. |

Если в проекте нет SDD-инструмента, остановись. Скажи пользователю: "Библиотека рассчитана на проекты со SDD. В проекте не найден SDD-инструмент." Жди решения пользователя.

## Этап 3. Правила и шаблоны

Цель: создать файл правил и шаблоны гайдов. Скопируй тексты ниже без изменений.

### Шаг 3.1. Создай `docs/DOCS-RULES.md`

Скопируй этот текст:

````markdown
# Правила документации проекта

Этот файл — единый источник правил. Навыки и агенты ссылаются на него.

Не меняй номера разделов. Навыки и конфиги ссылаются на них.
Ссылайся на раздел так: раздел 7 "Проверка".

## 1. Структура

- Карта проекта: `docs/MAP.md`. Новый человек начинает с этого файла.
  Карта также показывает, к какой области относится путь в коде. Один путь относится к одной области.
- Маршрут чтения по ролям: `docs/ONBOARDING.md`.
- Словарь: `docs/glossary.md`.
- Гайды: `docs/guide/<область>/analyst.md` и `docs/guide/<область>/dev.md`.
- Шаблоны: `docs/guide/_template/`.

## 2. Правила письма

1. Одно предложение — одно действие или один факт.
2. Предложение — не длиннее 20 слов. Максимум 25.
3. Пиши в активном залоге.
   - Плохо: "Книга сохраняется в БД".
   - Хорошо: "`BookRepository` сохраняет книгу в БД".
4. Для доменных понятий используй только термины из `docs/glossary.md`. Используй их в значении из словаря.
5. Не заменяй термин синонимом. Повтор термина — это норма.
6. Имена классов, методов, файлов, таблиц пиши в `обратных кавычках`.
7. Условие пиши так: `Если <условие>, <кто> <действие>.`
8. Предупреждение пиши так: сначала команда, потом причина.
   - "Не вызывайте `save()` в цикле. Это создает много запросов к БД."
9. Гайд — не больше одного экрана (около 60 строк). Если больше — раздели область.
10. Не пиши вводные фразы: "следует отметить", "в рамках", "осуществляет", "данный".
11. Если факт не проверен, пиши `[ПРОВЕРИТЬ: <что>]`.
12. Не вставляй в гайд код длиннее 5 строк. Дай ссылку на класс. Скопированный код устаревает первым.

## 3. Два вида гайдов

| | `analyst.md` | `dev.md` |
|---|---|---|
| Читатель | Аналитик | Разработчик |
| Отвечает на вопрос | Что и зачем? | Как и где? |
| Имена классов | Нет | Да |
| Разделы | Назначение, Бизнес-правила, Пример | Точка входа, Как работает, Как изменить, Внимание |

Под заголовком каждого гайда стоит строка проверки:

```markdown
> Проверено: 2026-10-31, коммит `a1b2c3d`
```

Дата — день проверки. Хеш получи командой `git rev-parse --short HEAD`.

## 4. Словарь

1. Один термин = одно значение.
2. Новый термин сначала добавь в словарь. Только потом используй.
3. Если слово имеет два значения в проекте, сделай два составных термина.
   Пример: не "номер", а "номер книги" и "номер читателя".
4. Запрещенные синонимы перечисли в колонке "Не использовать".
5. Не удаляй термин, если он есть в спецификациях или гайдах.
6. Если термин переименован, замени его во всех гайдах. Старое имя добавь в колонку "Не использовать".
   В спецификациях замени термин через обычный процесс изменения спецификаций.

## 5. Когда обновлять

Обнови гайды области, если изменилось:
- требование в спецификации области;
- точка входа, порядок шагов или условия в коде;
- имя класса или метода, который упомянут в гайде;
- термин в словаре.

Обнови `docs/MAP.md`, если изменилось:
- список областей или их имена;
- путь к спецификации, коду или гайду области;
- владелец области.

Обнови `docs/ONBOARDING.md`, если:
- добавлена область, важная для новичка;
- удален или переименован гайд из маршрута чтения.

## 6. Как обновлять

1. Определи измененные области:
   - если есть папка текущего изменения в спецификациях, используй ее;
   - иначе выполни `git diff --name-only <база>` и найди области по `docs/MAP.md`;
   - если не можешь определить области, спроси пользователя.

   `<база>` — ветка, от которой начата работа. Например, `main`.
2. Найди новые доменные слова. Добавь их в словарь.
3. Измени только затронутые разделы гайдов.
4. Удали из гайдов описание удаленного поведения.
5. Обнови `docs/MAP.md` и `docs/ONBOARDING.md` по разделу 5 "Когда обновлять".
6. Выполни раздел 7 "Проверка". Исправь все пункты "нет".
7. Обнови строку "Проверено" в каждом измененном гайде.

## 7. Проверка

Проверяй каждый измененный файл по списку. Для каждого пункта запиши "да" или "нет + где".

**Связь с кодом (dev.md):**
- [ ] Для каждого имени в `обратных кавычках`: я открыл файл и нашел это имя.
- [ ] Шаги "Как работает" идут в том же порядке, что и в коде.
- [ ] Условия "Если …" совпадают с условиями в коде.

**Связь со спецификацией (analyst.md):**
- [ ] Каждое требование спецификации отражено в "Бизнес-правилах".
- [ ] В "Бизнес-правилах" нет правил, которых нет в спецификации или коде.

**Термины (оба гайда):**
- [ ] Все доменные слова есть в словаре.
- [ ] Нет слов из колонки "Не использовать".
- [ ] Каждый термин использован в значении из словаря.

**Стиль (оба гайда):**
- [ ] Каждое предложение — не длиннее 25 слов.
- [ ] Один шаг — одно действие.
- [ ] В `analyst.md` нет имен классов.
- [ ] Гайд не длиннее ~60 строк.
- [ ] Нет кода длиннее 5 строк.
- [ ] Нет пометок `[ПРОВЕРИТЬ]` (или они переданы пользователю).

**Словарь (если изменен):**
````
