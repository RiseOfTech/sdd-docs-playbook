# Задача: изучить проект перед внедрением документации

Ты — ИИ-агент. Ты работаешь в репозитории проекта.
Прочитай эту инструкцию полностью. Затем выполняй шаги по порядку.

Цель: понять, что за проект и какие инструменты уже есть.
Результат: файлы `docs/_setup/inventory.md` и `docs/_setup/progress.md`.

## Главные правила

1. Выполняй шаги строго по порядку. Не пропускай шаги.
2. На шаге с пометкой **СТОП** покажи результат пользователю. Жди ответа. Не продолжай без ответа.
3. Создавай только файлы `docs/_setup/inventory.md` и `docs/_setup/progress.md`.
4. Не изменяй код программы и спецификации.
5. Не придумывай имена классов, методов, файлов, полей.
   Каждое имя копируй из файла, который ты открыл в этой сессии.
6. Если ты не уверен в факте, напиши в тексте `[ПРОВЕРИТЬ: <что именно>]`. Не угадывай.
7. Не делай коммиты и не создавай ветки, если пользователь не попросил.
8. Если инструкция противоречит правилам проекта (`AGENTS.md`, `CLAUDE.md`, `GIGACODE.md` и т. п.), остановись и спроси пользователя.

**Если работа прервалась:** открой `docs/_setup/inventory.md`. Продолжи с первого незаполненного раздела.

## Шаг 0. Выбери корень документации

Корень документации — папка, в которой лежат все файлы документации. По умолчанию это `docs/`.

1. Проверь корень проекта. Найди папки с файлами `.md`, например `docs/`, `documentation/`, `wiki/`.
2. Если папки `docs/` нет, а другая папка с документацией есть, остановись. Спроси пользователя: "Документация проекта лежит в `<папка>/`. Создать файлы документации в ней или в новой папке `docs/`?"
3. Запиши ответ. Это корень документации.
4. Если корень документации не `docs/`, во всех путях этого промпта замени `docs/` на корень документации. Пример: `docs/_setup/inventory.md` станет `documentation/_setup/inventory.md`.

В остальных случаях корень документации — `docs/`.

## Шаг 1. Найди файлы и запиши, что нашел

Проверь каждый пункт. Для каждого запиши: "есть" (путь) или "нет".

**Сборка и язык:**
- `build.gradle`, `build.gradle.kts`, `settings.gradle*`, `pom.xml`, `package.json`, другие.
- Модули проекта (из `settings.gradle` или `pom.xml`).

**Спецификации (SDD):**
- `openspec/` — OpenSpec. Запиши: `openspec/specs/*`, `openspec/changes/*`, `openspec/config.yaml`.
- `.specify/` или `specs/` — Spec Kit или другой инструмент.
- Другие папки со спецификациями или требованиями.

**Инструкции для агентов:**
- `AGENTS.md`, `CLAUDE.md`, `GIGACODE.md` (в корне и в подпапках).
- `.claude/skills/*/SKILL.md`, `.claude/commands/*`, `.claude/agents/*`.
- `.gigacode/skills/*/SKILL.md`, `.gigacode/commands/*`.
- `.opencode/skills/*/SKILL.md`, `.agents/skills/*/SKILL.md`.
- `.cursor/rules/*`, `.github/copilot-instructions.md`, другие файлы с правилами для ИИ.
- Правила и навыки вне репозитория. Признак: файл инструкций ссылается на путь вне проекта, например `~/.config/<инструмент>/AGENTS.md` или `~/.claude/skills/`. Запиши путь. Не открывай файл. Добавь вопрос пользователю: учитывать ли этот файл.

**Документация:**
- `README.md`, `docs/`, `wiki/`, `adr/`, другие папки с `.md`.
- Словари и списки терминов. Ищи и отдельные файлы, и разделы внутри документов. Например, раздел "Термины" в `README.md`. Запиши путь и название раздела.

**Язык документации:**
- На каком языке написаны спецификации и документация проекта.

**Предметная область (поиск):**
- Главные пакеты с бизнес-логикой (например, `domain`, `service`, `model`).
- SQL-скрипты, схемы данных.

## Шаг 2. Прочитай найденные навыки, правила и документы

Для каждого навыка и файла правил запиши одну строку:
`<путь> — <что делает> — <когда запускается>`.

Отметь навыки, которые связаны с: ревью, задачами, спецификациями, документацией.

Для каждого документа из раздела "Документация" шага 1 выбери оценку:
- "актуален" — факты из документа совпадают с кодом;
- "частично устарел" — часть фактов не совпадает с кодом;
- "устарел" — документ описывает поведение или процесс, которых больше нет;
- "неизвестно" — ты не смог сверить факты.

Чтобы выбрать оценку, сверь с кодом 2–3 факта из документа: имена классов, настройки, зависимости. Запиши основание: какой факт совпал или не совпал.

## Шаг 3. Определи области (capability)

- Если есть `openspec/specs/<имя>/`, каждая папка = одна область.
- Если есть другой SDD-инструмент, используй его деление.
- Если SDD-инструмента нет, добавь вопрос пользователю: "Библиотека рассчитана на проекты со SDD. В проекте не найден SDD-инструмент. Продолжать?" Предложи области по модулям или пакетам бизнес-логики.
- Если спецификации разбиты по этапам работы, а не по областям, не используй их деление. Предложи области по коду. Добавь вопрос пользователю.

Запиши список областей. Для каждой: имя, путь к спецификации (если есть), пути к коду.

Пути к коду:
- Если у области своя папка или пакет, запиши путь к нему.
- Если код разделен по слоям (например, `controller`, `service`, `repository`), у всех областей одни и те же пакеты. Тогда запиши для каждого слоя файлы области или маску имен. Пример для сервиса библиотеки: `service/Loan*`, `repository/LoanRepository.java`.
- Каждый путь относится только к одной области. Если файл нужен двум областям, добавь вопрос пользователю.

```markdown
|---|---|---|---|

<язык спецификаций и документации>

|---|---|---|
```

Если язык проекта не совпадает с языком этого промпта, добавь вопрос: на каком языке писать документацию. Для русского языка используй папку библиотеки `ru/`, для английского — `en/`.

```markdown
- [ ] 04. Встраивание в процесс

## Области
| Область | analyst.md | dev.md | Проверено |
|---|---|---|---|
```

**СТОП.** Покажи пользователю `inventory.md`. Задай вопросы из раздела "Вопросы к пользователю". Жди ответа.
